Nigerian Fintech Transactions Intelligence Platform

Power BI on a live PostgreSQL star schemaSynthetic data, 50,000 transactions
Problem

A fintech needs one trusted view of where money moves, where revenue comes from, and where payment risk concentrates. The harder requirement is the plumbing underneath: data has to be ingested, enriched, stored in a real database, and modeled before a single chart is drawn.

Architecture
Python data generation → live FX API enrichment → PostgreSQL star schema → Power BI model → DAX measures → dashboard
Approach

Engineered a synthetic dataset of 50,000 transactions across 2,000 customers, modeling realistic Nigerian channel mix and a built-in reversal rate. A Python ETL pipeline calls a live exchange-rate API (with error handling and a fallback rate) to convert every transaction to USD, then loads four tables into PostgreSQL structured as a star schema: a transactions fact table linked to customer, channel, and a dedicated date dimension. Power BI connects directly to the live database, where I built the model and the DAX measures behind every figure.

Questions it answers
  • How do revenue and transaction volume trend month over month?
  • Which channels and cities drive activity, and which customer segments generate revenue?
  • Where do payment reversals concentrate, and what is the exposure?
Technical highlights

Star-schema model with a dedicated date dimension for time intelligence. A reversal-rate measure built on CALCULATE with safe DIVIDE, and month-over-month growth via DATEADD. API integration with graceful fallback. Every USD figure stores the FX rate used, so the conversion is fully auditable.

Outcome

A living BI system, not a static file: refresh the pipeline and the report follows. The dashboard surfaces a USSD and Mobile-led channel mix, Retail-dominated revenue, and a 3.95% reversal rate consistent end to end from generation through to DAX.

E-Commerce Sales, Margin & Retention Analytics Platform

Power BI on a live PostgreSQL star schemaSynthetic data, ~120,000 line items
Problem

A multi-category online retailer needs to see not just sales, but profitability by category and whether it is actually retaining customers over time. That demands modeling at the right grain and analytics beyond simple totals.

Architecture
Python data generation → live FX API enrichment → PostgreSQL star schema → Power BI model → DAX measures → dashboard
Approach

Engineered a synthetic retail dataset of 40,000 orders expanded to roughly 120,000 line items across 90 products and 3,000 customers. The fact table is modeled at line-item granularity, so analysis rolls up cleanly from product to order to category while preserving per-line price and cost for accurate margin. A Python ETL pipeline loads four tables into a PostgreSQL star schema; Power BI connects to the live database for the model and DAX layer.

Questions it answers
  • Which categories drive revenue, and which actually drive profit and margin?
  • How does revenue trend over time across the catalogue?
  • Are we retaining customers? How does each signup cohort behave month over month?
Technical highlights

Revenue and cost computed with SUMX at row level; orders counted with DISTINCTCOUNT to respect the line-item grain. A full cohort retention analysis rendered as a shaded matrix, with cohort size fixed via ALLEXCEPT so the denominator holds to the signup cohort while the numerator tracks the active period. Margin analysis separating absolute profit from margin rate per category.

Outcome

An executive view that distinguishes high-revenue categories from high-margin ones (Electronics leads revenue and profit at roughly 35% margin) and a retention heatmap that makes customer churn visible at a glance, on a refreshable pipeline rather than a static extract.

Telecom Customer Churn & ARPU Analytics Platform

Power BI on a live PostgreSQL star schemaSynthetic data, 5,000 subscribers
Problem

A mobile operator needs to know not just how much revenue it earns, but where that revenue concentrates and which customers it is losing. Two metrics drive the business: ARPU (average revenue per user) and churn rate, and the real question is how they relate across plan tiers.

Architecture
Python data generation → PostgreSQL star schema → Power BI model → DAX measures → dashboard
Approach

Engineered a synthetic base of 5,000 subscribers across four prepaid and postpaid plans, with usage modeled at customer-month granularity (calls, data, SMS, revenue) and churn probability deliberately tied to plan tier. Loaded into a PostgreSQL star schema; Power BI connects live for the model and the DAX metrics layer.

Questions it answers
  • What is ARPU, and how does it differ across plan tiers?
  • What is the churn rate, and which segments are leaking customers?
  • Do the customers who churn differ in value from those who stay?
Technical highlights

ARPU computed over customer-months; churn rate built on a customer-level flag with CALCULATE. A calculated plan dimension on the customer table so churn cross-filters correctly by plan. Comparative measures for ARPU of retained versus churned customers, tying the two headline metrics together.

Outcome

The dashboard surfaces the core telecom tension at a glance: premium postpaid customers generate over ten times the ARPU of basic prepaid yet churn at a fraction of the rate (roughly 4% versus 35%). The highest-value segment is also the stickiest, a direct steer for where retention effort pays off.

Accounts Payable Controls & Compliance Analytics Platform

Power BI on a live PostgreSQL galaxy schemaSynthetic data, 8,000 invoices
Problem

An accounts-payable function needs more than a spend report. It needs controls: visibility into overdue exposure, whether payments meet agreed terms, and whether the same invoice has been paid twice. These are the questions an auditor actually asks.

Architecture
Python data generation → PostgreSQL galaxy schema → Power BI model → DAX measures → controls dashboard
Approach

Engineered a synthetic dataset of 8,000 invoices and ~7,000 payments across 150 vendors, with realistic anomalies deliberately built in: unpaid invoices that age, late payments against agreed terms, and duplicate payments concentrated among a small set of problem vendors. Modeled as a galaxy schema in PostgreSQL: separate invoice and payment fact tables sharing conformed vendor and date dimensions. Power BI connects live for the model and the DAX controls layer.

Questions it answers
  • How much is outstanding, and how overdue is it by aging bucket?
  • Are we paying on time? How does due-date compliance trend?
  • Which invoices were paid more than once, and which vendors drive that risk?
Technical highlights

Outstanding payables computed with set logic over unpaid invoices. A duplicate-payment detector mirroring an SQL HAVING COUNT > 1 audit query, surfaced live in DAX. Due-date compliance via a row-level Days Late calculation, and aging buckets via SWITCH. The analysis pinpoints that a handful of vendors account for the majority of duplicate-payment exposure.

Outcome

A controls dashboard an internal-audit or treasury function could use directly: aging exposure, on-time payment rate, and the specific vendors driving duplicate-payment risk, all on a refreshable pipeline.

03SQL, in my own hand

Dashboards are the surface. The querying underneath is where the analysis happens. A few representative queries from my work, covering window functions, CTEs, and conditional aggregation.

Top sales rep per region by total revenueCTE · MAX · multi-join
WITH rep_sales AS (
  SELECT r.name AS region, s.name AS rep,
         SUM(o.total_amt_usd) AS total_sales
  FROM orders o
  JOIN accounts a   ON a.id = o.account_id
  JOIN sales_reps s ON s.id = a.sales_rep_id
  JOIN region r     ON r.id = s.region_id
  GROUP BY 1, 2
),
peak AS (
  SELECT region, MAX(total_sales) AS max_sales
  FROM rep_sales GROUP BY 1
)
SELECT rs.rep, rs.region, rs.total_sales
FROM rep_sales rs
JOIN peak p
  ON p.region = rs.region AND p.max_sales = rs.total_sales
ORDER BY rs.total_sales DESC;
Running total of revenue, partitioned by yearwindow function · PARTITION BY
SELECT standard_amt_usd,
       DATE_TRUNC('year', occurred_at) AS yr,
       SUM(standard_amt_usd) OVER (
         PARTITION BY DATE_TRUNC('year', occurred_at)
         ORDER BY occurred_at
       ) AS running_total
FROM orders;
Customer lifetime-value tiersCASE · conditional aggregation
SELECT a.name,
       SUM(o.total_amt_usd) AS lifetime_value,
       CASE WHEN SUM(o.total_amt_usd) > 200000 THEN 'Top'
            WHEN SUM(o.total_amt_usd) > 100000 THEN 'Middle'
            ELSE 'Low' END AS tier
FROM orders o
JOIN accounts a ON a.id = o.account_id
GROUP BY 1
ORDER BY 2 DESC;
